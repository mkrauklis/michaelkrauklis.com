3 — query, key, value

The step almost every explainer skips

Each token's embedding gets projected three different ways — three learned lenses on the same fingerprint, called Query, Key, and Value. Think of a library: your Query is what you type into the search bar, every book's Key is its catalog listing, and the Value is what's actually inside once you pick it up.

📚 Query — what this word is looking for. Key — what this word has to offer, to anyone looking. Value — what it actually contributes, once picked. Real models run several of these lenses in parallel, called heads — see "Go deeper" below.

4 — attention itself

Who's looking at whom

Every word's Query asks every word's Key how relevant it is. Those raw scores get squeezed through softmax into weights that sum to exactly 1 — the model is forced to spend its full attention budget across the sentence, it just chooses how to split it. Those weights then blend the Values into each word's new, context-aware output. Click a word to spotlight what it's attending to.

thicker / brighter = more attention click a word to spotlight its attention

⚠ What's real here, and what isn't: the dot products, the softmax, and the blending are exactly the real operation. What's not real is which words end up mattering to which — these Query/Key lenses are fixed, untrained numbers, not weights learned from billions of real sentences. In an actual trained model, that's what makes "bank" attend differently near "river" than near "loan." Here, the mechanism is authentic; the judgment behind it isn't. See "How this actually works" below for why that trade was made on purpose.

5 — the kv cache

Now watch it generate, one token at a time

Everything above treated your sentence as fully typed and analyzed at once. A real chatbot writes its reply one token at a time instead — and that's the only situation where a KV cache makes sense. Once a token's Key and Value are computed, they never change (they only depend on that token and the ones before it) — only a fresh Query gets computed at each new step. Click "Generate next token" below and watch this table grow.

With the cache off, every new token forces a full recomputation of every row so far (watch the whole table flash) — wasteful, since nothing about the earlier rows actually changed. With it on, only the new row lights up. Either way the output is identical — this is a real speed/redundancy difference, never a correctness one.

6 — prediction

What comes next?

The last token's context-aware output gets projected once more and compared against a list of candidate next words — the closer the match, the higher the probability. Pick one yourself, or let the top pick auto-select, and the whole pipeline — tokenize, embed, attend, cache — visibly reruns for one more step.

How this actually works — for anyone curious, no math background needed

Every real computation on this page runs on your own words, live, entirely in your browser — nothing you type is sent anywhere. The one thing that's not real is the starting material: normally these numbers come from months of training on real text. Here, that training never happened.

Why the embeddings and projections are fixed, not trained

Every token's embedding here is a deterministic fingerprint generated from the word's own spelling (a seeded hash, not a lookup into any real vocabulary) — "bank" always gets the exact same 16 numbers, but those numbers carry no relationship to "river," "loan," or anything else. The Query, Key, and Value projections are small, fixed random matrices too. That was a deliberate choice, not a shortcut taken lightly: a real pretrained embedding table would make Stage 1's fingerprints "mean" something, but the attention pattern you actually watch in Stage 4 is driven by the Query/Key projections, not the embeddings themselves — and those projections would still be untrained, fixed, random numbers either way. Shipping a real embedding table would have added real asset weight for a benefit that doesn't survive to the part you actually watch. So: the mechanism (every dot product, softmax, and weighted blend) is 100% real and exactly what a trained model does. The judgment behind which words end up mattering to which is not — that's what training on real language actually buys you, and it's honestly out of scope for a page that runs entirely in a browser tab with no server and no training step.

Tokenization

Real tokenizers (like BPE, used by GPT-style models) learn their word-splitting rules from millions of real documents. This page uses a much simpler stand-in: split on whitespace, peel off trailing punctuation as its own token, and split a long word before a common suffix (like -ing or -tion), marking the split piece with a leading ## the same way real subword tokenizers do. It's a simplified approximation built to make the "words sometimes split into pieces" idea visible and genuinely happen sometimes — not a reimplementation of BPE itself.

Positional encoding

This one is the real formula from the original paper — alternating sine and cosine waves at different frequencies per position, added directly on top of the embedding. No shortcuts here: this is exactly how real transformers inject word order.

Attention

Real scaled dot-product attention: for every pair of tokens, the Query of one is dotted with the Key of the other, divided by the square root of the projection size (keeps the numbers from blowing up as dimensions grow), and every token's full row of scores is run through softmax so it sums to exactly 1. Those weights are the literal thickness/brightness of the threads you saw in Stage 4. The final output for a token is a weighted sum of every token's Value, using those exact weights — also real, also exactly what a trained model does with its own (trained) numbers.

The KV cache

Keys and Values only ever depend on a token and the ones before it, which is why they never need to be recomputed once they exist — a fact that's true in any real model, trained or not, since it's a property of the causal generation setup, not of what the numbers happen to be. The "redundant computations avoided" counter is a real count of how many rows a naive from-scratch implementation would have recomputed at each step that this page's cache-on path skipped — it's not measuring actual wall-clock time (everything here is small enough to be instant either way), just the real structural redundancy the cache exists to eliminate.

Predicting the next token

A real language model's final layer projects its last hidden state back into vocabulary space and picks a probability for literally every word it knows. This page does the same kind of projection — one more fixed matrix maps the attention output back into embedding space, then compares that against a candidate word list using the exact same dot-product similarity attention itself uses — but the candidate list is a few hundred common English words, not a real vocabulary, and the matrix is untrained. That's why generated continuations read as plausible-looking word soup rather than fluent language: the mechanism (project, compare, softmax, sample) is real; the fluency a trained model has learned is not.
